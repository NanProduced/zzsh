# 多端扩展与 BFF 边界

日期：2026-09-08。Owner 已明确：先做 Web，后续支持 iOS、Android 和微信小程序；各前端通过面向自身的 BFF 接入业务后端。本文件约束多端边界；当前已实现认证 BFF 与数据库接入，完整交易业务尚未完成。

## 逻辑分层

```text
用户 Web ── Next.js 服务端 / Web BFF ────────┐
管理 Web ── Admin BFF ──────────────────────┤
iOS / Android ── App BFF（后续）────────────┼─ NestJS 业务模块 ─ PostgreSQL
微信小程序 ── 小程序 BFF（后续）─────────────┘
支付等第三方 ── 专用回调入口 ────────────────┘
```

BFF 是服务端的客户端适配职责，不是每端必须增加一个独立进程。初期 Web BFF 放在 Next.js 服务端；Vite 仅构建浏览器应用，不能充当服务端 BFF。Admin BFF 可作为 apps/api 内独立模块，调用内部应用服务，不为同进程调用额外绕一圈 HTTP。App 与小程序适配模块在实际开发时建立；仅在运行、依赖或发布需求不同且收益明确时拆成独立部署。

NestJS 业务层不依赖 Next.js、浏览器 Cookie、DOM、小程序运行时或客户端页面结构。所有持久化写入与第三方资金动作从业务层进入。BFF 不直连交易数据库，不复制计价、押金、权限或结算规则。

Next Server Components 可调用服务端的 Web BFF 适配函数再访问业务 API，不需要 HTTP 请求自己的 Route Handler。只有浏览器需要的端点才暴露为公开路由。Server Actions 可用于 Web 交互，但不能作为 App/小程序唯一业务契约。

## 职责分配

| 层次 | 负责 | 不负责 |
|---|---|---|
| 客户端 | 展示、交互、平台 SDK、加载和失败提示 | 最终价格、权限判定、支付完成判定 |
| BFF | 会话适配、请求聚合、字段裁剪、分页与视图数据、平台交互参数包装 | 数据库写入、重新计算业务金额、跨多个请求模拟资金事务 |
| NestJS 业务层 | 用户身份、对象归属、授权、账号占用、订单、金额、支付、退款、履约记录、审计和幂等 | HTML、平台控件和端专属页面布局 |

同一业务在各端返回可不同，但核心状态、金额、错误语义必须一致。聚合读取部分失败可以明确标注；资金写入不能用多个 BFF 请求拼接成假事务。第三方回调进入专用服务端入口，不经过浏览器、页面会话或客户端 BFF。

## 身份与权限

- 内部用户 ID 独立于手机号、openid、unionid、设备 ID。外部身份按提供方、应用标识和主体建立关联；不能假设不同 AppID 的 openid 相同，也不能假设 unionid 总可获得。绑定、解绑和账号合并需要身份验证。
- Web 会话优先评估 HttpOnly/Secure Cookie，并配套 CSRF/Origin 防护；App/小程序采用各自适用的令牌与存储机制，统一支持过期、撤销和退出。具体认证协议在认证设计时冻结。
- NestJS 仍须校验已验证的终端用户及数据范围。BFF 的服务凭据不能代替用户授权；不能信任客户端随意提供的 userId、role、X-User-* 或 clientType。
- 管理员身份与权限范围独立控制。跨域 CORS 不是认证机制，接口位于内网也不是免授权理由。
- 个人订单、余额、实名和后台数据不得进入公共缓存。BFF 不透传全部 Cookie、Authorization、原始第三方响应或任意目标 URL。

## 可长期演进的接口契约

- 第一个真实业务接口开始制定版本策略（优先 /api/v1），健康探针保持独立。不因每次加字段升级版本；破坏性变更提供兼容窗口与迁移说明。
- App 无法像 Web 一样即时全量更新，服务端须明确支持的客户端版本；不要删除旧字段或改变枚举含义而要求全部用户立刻升级。客户端对未知枚举有安全显示与拒绝危险操作的行为。
- OpenAPI 是语言无关契约；按需求生成 TypeScript 或移动端客户端。运行时输入校验不可由 TypeScript 类型替代，不公开 ORM 实体作为契约。
- ID 按字符串传输；金额使用有明确币种、单位、精度的十进制字符串；时间使用带时区的标准格式。BFF 不把金额变为浮点后再传递。
- 统一机器可识别错误码和 requestId。前端文案可本地化，不能靠匹配中文错误字符串执行流程；不返回堆栈或内部秘密。
- 筛选使用稳定属性 ID、明确 ANY/ALL 和范围语义；JSONB 不代表字段可随意改类型。排序有稳定次级键，分页策略在业务数据规模确定后选择。
- 所有有副作用的重试由业务接口明确幂等语义；BFF 透传并正确约束幂等键，不在每次重试重生成键。支付超时不等于失败，不自动重新付款。

## 平台差异单独适配

| 能力 | 开发约束 |
|---|---|
| 支付 | 订单与收款事实统一；二维码、H5跳转、原生SDK和小程序支付参数按渠道/终端返回带类型的数据。客户端跳转成功不等于付款成功。App与小程序的可用支付方式、资质和审核要求在上线前核实，不把Web汇聚支付原样可用视为前提。 |
| 客服 | 统一记录交接状态，BFF提供适合终端的打开方式及失败回退。点击、成功唤起、实际添加、人工接待分别记录，不能混为已交付。 |
| 上传 | 后端先授权、限制类型/大小与归属；客户端可按方案直传对象存储，业务层确认附件。签名上传或私密下载可以直达存储，不要求大文件经BFF代理；不能暴露存储密钥。 |
| 弱网/后台恢复 | 允许查询订单最终状态、分页重试、取消过时读取。App回到前台需重新核验状态；不离线自动提交资金动作。 |
| 通知与深链接 | 站内状态为事实；短信、推送和小程序通知只是触达方式。链接用稳定资源ID，不把凭据或敏感订单详情放URL。平台跳转失败提供安全回退。 |
| 网络 | 小程序、原生App、浏览器有不同运行与域名限制；在接入阶段核验HTTPS、域名配置、Cookie/令牌、超时和平台审核，不把开发工具放宽限制当验收。 |

## Monorepo 与复用范围

当前 packages/ui 只有 Web CSS，它不是原生 UI 库。shadcn/DOM 组件不承诺直接用于原生 App 或微信小程序。可复用的是品牌 token 的语义、API 契约、无平台依赖的格式化/校验工具及最重要的服务端业务规则。

不要让共享契约依赖 Node-only 模块、浏览器存储、React 或 Nest 装饰器。依赖方向为客户端/BFF依赖契约、业务层实现规则；不能让业务层反向依赖客户端。只有第二个真实调用方或明确契约需要时才创建共享包；当前不创建空的 mobile/miniprogram/BFF workspace。

## 功能开发验收

每个新业务功能至少回答：

1. 换成不具备 Cookie/DOM 的客户端，业务动作是否仍可完成？
2. 是否重复实现计价、状态迁移、授权或资金规则？
3. 用户身份如何被验证并传递，服务端是否检查对象归属？
4. 旧客户端、未知枚举、弱网重试和重复提交如何处理？
5. 相同业务经不同 BFF 是否保持相同金额与状态？
6. 契约测试、运行时输入验证和日志脱敏是否覆盖边界？

这些是设计检查，不要求现在编写未来客户端的空测试。Web 首期完成对应业务的核心服务测试与 BFF 契约测试；后续新增端复用核心验收，再补平台真机验证。
