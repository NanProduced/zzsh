# 信用与号主保证金运行合同

信用/保证金纯读在认证应用中常态挂载。部署profile默认装配信用/保证金命令与新用户初始化；`CREDIT_GUARANTEE_ENABLED=false`仅供隔离本地夹具。能力装配不代表有已发布政策、可用资金或渠道授权；供给仍核原G0政策/proof门禁，既有责任不会因预览关闭命令而消失。

Owner 已核实旧平台当前没有未退的上架保证金；按[迁移范围](legacy-data-mapping.md#已确认的旧数据迁移范围)，旧上架保证金及其收退记录不迁入新平台。新目标要移除旧上架保证金专属运行逻辑、接口、表和字段；源数据筛选仍须识别并跳过该专项，既有历史迁移须保持可重放。此为待实施目标，既有代码和旧测试库仍可能包含旧保证金观察；不能将“不迁入”解释为源库从未有记录，也不能因去除旧专项而停用新平台信用、号主保证金或租客押金。

正式应用必须已完成迁移`0067_credit_guarantee_contract`和`applyRuntimePrivileges`。启动始终检查七张表可读、`zzsh_credit.runtime_contract_version()=1`及runtime不能CREATE该schema；缺失/部分部署/权限错误阻止启动，不因命令关闭而跳过。运行中依赖故障维持UNKNOWN并拒绝新发布/确认/建单，不退回免缴；读取装配不执行迁移、赋权或回填。

本人信用overview使用`readCreditSnapshot(...,false)`，不建立100分状态或INITIALIZED事件。返回`creditState=INITIALIZED|NOT_INITIALIZED`，缺档案时`credit=null`并保留原保证金/恢复申请/收退尝试的读取；不能据缺档案或空责任列表推断免缴、零信用或历史资金已清。客户端遇旧服务缺少creditState时保留UNKNOWN。读取保持身份、session、对象/游戏权限及原事务复核锁，不开放恢复申请、支付、退款或管理员决策；这些命令仍要求原部署能力与正式权限。

初始信用100属于新平台政策；0067为执行迁移时已有的用户建立初始状态和INITIALIZED事件。之后承接的主体通过正式初始化维护入口补齐缺失档案，保留已有分数、版本和事件；schema存在和GET读取均不表示主体已初始化。四项管理权限不自动授角色/游戏范围。启用后的新用户注册在原事务初始化信用；分销/原生钱包初始化顺序和独立准入边界保持。保证金沿既有经济根、finance_event与ledger记账，不增加第二总账。

信用初始化与旧消费成长维护沿业务原包＋独立执行批准两文件绑定。v1批准继续严格核测试metadata表；真实资源的v2批准须显式指定`DATABASE_COMMENT`，由同一业务连接核准确库名/OID/owner/current_user及数据库COMMENT，不因缺测试表自动回退或补建标记。当前Boss/会话、DB时钟、原权限和成长APPLY表owner守卫保持；更换执行批准不改变原业务包/key/指纹，UNKNOWN仍沿原身份与回执恢复。

正式发布、个人确认和建单共用信用/coverage权威读取：credit state与存在的requirement通过同一业务PoolClient持FOR SHARE，写方FOR UPDATE；锁至事务提交/回滚释放。信用/coverage版本封入既有guarantee.reference摘要，个人ruleRefs仍严格五键，listingHash完整绑定原发布资料。启用状态变更应先处理未决责任，不静默换key或签名正文。

原保证金支付意图先校主体/账号，再按原key读取冻结回执；当前政策/版本异常不能截断原回执恢复。只有没有原回执的新请求读取当前权威依据。Admin明细先按game scope筛requirement，支付/退款各自返回完整历史，不以最新摘要替代旧事实。

号主主动永久下架、该出租记录未曾开租且无未决占用时，系统在下架事务中按已确认的原保证金付款金额建立自动退还责任，无需人工审批；同一原款只产生一笔有效退款。其他账号的在架或订单不阻碍该账号退还；原付款不明、重复或本账号历史责任不明时阻断下架并由客服核对。系统批准和退款请求不等于渠道到账；当前保证金真实收退款渠道执行仍待接入和验证。

主动下架时如保证金付款结果不明、退款资格待核或应退责任无法落库，整笔下架事务回滚并提示联系客服；不能以一条不确定的责任冒充退款。若异常时序下已下架账号后来收到可信付款确认，保留收款事实，并在账号与原责任锁内重新检查能否建立原款退款。收款与退款观察按账号、责任、原款顺序加锁，重放只恢复原责任。退款失败或付款依据不足仍交客服，不把失败当作退回。

尚未发布的草稿修改并重新报价后，如已登记保证金金额与新要求不一致，发布前状态为待核；已发布账号仅因平台按时调整价格而继续接单时，原保证金依据不追补。

账号上架时，权威信用资格判定为免缴的，将明确的免缴事实与信用版本冻结在发布记录；后续信用下降不追缴。已缴情况复用上架时的保证金责任、金额和账本，后续信用变化不重新核算；退款或记录异常仍需按真实状态处理。免缴不能掩盖后来发现的本账号其他保证金未决款项。既没有免缴事实也没有可核对的已缴责任时保持待核。此保证金依据独立于新订单使用的价格及结算快照；新价切换和下单准入仍须完整适配。

0067保持原opening/提现/分佣规则，保证金CAPTURE/REFUND不增加钱包revision；runtime撤销表级和旧列级宽权限，再授精确写列，信用事件/对账记录只追加。该语义仍须在合法order-finance资源完成真实组合验证，纯测试或DDL静态核验不替代PG锁等待和账平证据。

真实汇聚提交/回调未开放。开启信用能力不启用真实支付、短信、实名或云信，受控结果记录仍受既有test/fake能力和资源范围约束。正式schema应用、既有65/draft结构采用、跨金融revision和关键F3 UI验收是独立门槛。

已登记的 ECS 测试或本地演示资源可提供保证金模拟收银：先创建本人账号的支付意图，再以原支付意图 ID 调用 `POST /api/v1/users/me/credit/accounts/:accountId/payment-intents/:paymentId/demo-confirm`，必须携带幂等键。仅登记后的本人新意图可确认；同一原请求重放读取原结果。账号下架后，测试 worker 仅处理同一登记资源的模拟原款对应的自动退款，复用保证金责任和账务处理；回执与审计标明模拟，`bankArrival=UNKNOWN`，不能当作汇聚或银行到账。未装配演示资源时不提供该测试入口。非演示环境启动时拒绝含该模拟回执的数据库，避免测试数据被当成真实保证金。用户侧模拟缴款入口仍需真实浏览器验收，正式商户渠道及其缴款界面尚未接入。
