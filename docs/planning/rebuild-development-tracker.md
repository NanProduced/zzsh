## 1. 目标与完成定义

目标不是翻译旧 Java/Vue 代码，而是在保持现有真实业务可接管的前提下，重新设计用户体验、运营流程、领域模型和资金治理。

Owner 补充确认（2026-09-09）：管理平台是重建核心交付，不仅要功能正确和 UI/UX 改善，还要发挥数据价值，为后续经营、供给、客服和财务分析建立可信基础。先完成旧后台功能覆盖与数据分析专项调研，再将经 Master 评审的必要采集、历史与口径要求分配到对应业务切片；不把数据基础统一拖到 M8，也不据此提前建设数仓或恢复已排除业务。

项目达到“可接管”至少同时满足：

1. 用户站、管理站和 API 可在本地稳定运行；PostgreSQL、Redis 由 Compose 提供，应用直接在主机启动。
2. 已证实的租号主链能够完成：注册/登录、实名、账号发布、审核上架、浏览下单、支付、云信客服履约、归还、结算、退款、收益入账和提现。
3. “改枪码”、公告和资讯具备与当前线上内容相匹配的读取及管理能力。
4. 所有资金动作区分业务应收应付、第三方真实现金流和对账结果；禁止通过直接改金额伪造事实。
5. 管理平台具备可配置权限、单人审批、不可变审计、异常任务、证据管理和财务对账工作流。
6. 历史数据可查询，在途业务可兼容处理；迁移可重复执行，所有资金差异均能解释。
7. 完成本地全流程验收、备份恢复演练和测试 ECS 部署演练后，才允许编制生产切换放行单。

首期不恢复未经证实仍在运营的账号出售、护航/代肝交易、通用商城、购物车、优惠券、秒杀、物流和页面装修系统。相关旧数据保留并按需要提供管理端历史查询。分销的新交易功能暂不恢复，但历史分销提成仍作为钱包资金来源迁移。

## 2. 不可破坏的设计约束

- 生产是单线切换：开发和测试期间旧平台继续运营；切换后旧平台停止对外服务和写入，不实行生产双写。
- PostgreSQL 是订单、资金、审批和审计的事实来源；Redis 只用于缓存、限流和任务协调。
- 用户账号与管理员账号、凭据和会话完全分离。
- 浏览、注册和登录不强制实名；首次付费租赁、发布账号和提现前必须实名。未满 18 周岁不得进入交易或资金流程。
- 提现沿用旧业务规则：收款人无需与平台实名姓名一致，但必须完整保存收款对象、执行证据、第三方单号、审批和对账状态。
- 高风险操作最多只需一名独立审批人；审批权限和适用条件动态配置，发起人不得审批自己的高风险申请。
- admin/root 可以破窗纠错，但只能追加冲销或更正记录，不能覆盖或删除原资金事实；破窗必须二次认证、留证据并通知 Owner。
- 审计日志及备注只追加、不可修改或删除；敏感内容按权限脱敏展示。
- 旧记录不按新规则重新计算。用户端不暴露新旧平台标签；管理端显示来源、迁移批次和兼容状态。
- 支付成功、云信接入成功、客服交付完成、用户成功登录和资金最终到账是不同事实，必须分别建模。
- 第三方适配器按当前官方契约实现；自动测试默认使用 fake，任何真实短信、OSS、支付、退款、代付、实名或云信调用都必须由专门命令和显式配置开启。
- UI/UX 不复制旧页面。用户站降低选择和理解成本；管理站围绕待办、异常、审批和对账工作流设计，不以堆叠表格作为默认方案。

## 3. 模块划分

| 模块 | 核心职责 | 明确边界 |
|---|---|---|
| `FND` 平台基础 | Compose、配置、数据库迁移、测试隔离、日志、requestId、探针、优雅退出 | 不承载业务状态机 |
| `IAM` 身份与访问 | 用户/管理员身份、会话、旧密码升级、短信、实名、年龄门槛、MFA、RBAC | 管理员身份不复用普通用户账号 |
| `GOV` 治理与证据 | 动态审批、不可变审计、备注、私有证据、破窗、更正 | 不直接修改领域金额或第三方结果 |
| `CAT` 游戏与内容 | 游戏、平台、上号方式、规则/协议版本、改枪码、公告、资讯 | 业务规则使用版本快照，不读取可变文案推导金额 |
| `SUP` 出租账号供给 | 草稿、版本、保证金、审核、上架、暂停、归档、媒体、对象归属 | 已上架关键变更必须重新审核 |
| `ORD` 报价与订单 | 服务端报价、订单快照、原子占号、超时释放、迟到支付、订单生命周期 | 一个账号最多一个有效占用；价格不由客户端决定 |
| `MON` 资金核心 | 支付尝试、Joinpay 事实、账本、冻结、退款、收益、提现、组合支付 | 外部成功不由页面跳转或人工填表推断 |
| `FUL` 客服履约 | 云信账号绑定、每单独立群、客服分配、交付清单、登录确认、归还验收 | 群聊只负责沟通，不替代平台结构化状态 |
| `SET` 结算与争议 | 消耗提交、双方确认、提前/到期结算、争议、申诉、保证金处理、全额包赔 | 裁决与付款审批分离 |
| `OPS` 运营与对账 | 异常中心、任务运行、Joinpay 账单导入、匹配、差异闭环、财务看板、通知 | 原始账单行不可编辑；未知资金不得自动生成业务单 |
| `MIG` 迁移与兼容 | 旧数据暂存、映射、来源标记、重复账号隔离、在途清单、可重复导入 | 反编译实体不是正式 DDL；以实际 MySQL 快照为准 |
| `REL` 交付与恢复 | 容器镜像、测试 ECS、监控、备份恢复、部署回滚、切换演练 | 新平台产生真实交易后不得恢复旧平台写入 |

Web、Admin、API 不是三个独立业务项目。每个业务里程碑应同时交付必要的 API、用户界面、管理工作流、审计和验证。

M1 基础

                                                    └─> M10 本地验收 ─> M11 ECS/切换演练

可以并行：

- 产品设计始终领先开发一个切片：M2 开发时设计 M3，M3 开发时设计 M4。

不可并行绕过：

- 未有 IAM/GOV，不开发可写管理功能。

## 8. Tracker 使用规则

状态只使用：`BACKLOG`、`READY`、`IN_PROGRESS`、`BLOCKED`、`REVIEW`、`DONE`、`CANCELLED`。

- 同一时间每个执行者只领取一个 `IN_PROGRESS` 任务。
- 任务开始前记录基线、允许修改路径和最小验证命令。
