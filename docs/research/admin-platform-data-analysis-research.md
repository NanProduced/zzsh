# 管理平台与数据分析基础专项调研

日期：2026-09-09。状态：`REVIEWED`，Master 已复核研究并作定向修订。研究完成；具体指标、产品设计及实现仍按后续任务评审，不授权业务实施。

## 1. 结论与证据边界

管理平台应同时承担经营判断、日常处理和证据追溯。首期优先把“发现问题 → 找到对象 → 安全处理 → 验证结果”做通；分析指标随着各业务切片建设，不能等到 M8 再补过去没有记录的事实。无需现在新增数仓、事件总线、BI 服务或独立管理业务后端。

- **已确认代码事实（C）**：仅指本地反编译实现或明确方法，不能证明线上启用、真实 DDL、权限生效和数据质量。
- **文档已确认（D）**：当前技术决定与 Tracker 的冻结约束。
- **浏览器可见事实（B）**：Owner 授权的当前已登录页面可见标签与结构，不证明统计准确或全部后台功能已验收。
- **推断（I）**：由代码行为推导的风险，尚未以真实数据或用户观察验证。
- **未知（U）**：生产启用、数据完整性、运行负载、岗位实际分工等未取得证据。
- **设计建议（R）**：本报告提出的目标、指标与任务候选，不是现有功能。

本文采用 product-manager-toolkit 的“业务问题 → 决策 → 验收”方法；没有访谈或流量证据，故不虚构 RICE 分数、收益或员工效率提升百分比。现有第三方研究仅作为带日期的项目材料引用，本轮没有刷新官方协议或商户能力。

冻结约束不变：Q104-C 允许非同名收款；一名独立审批人、禁止自审；组合支付完整设计但首发关闭；每单独立云信群、真人客服履约；提现余额区分号主收益、历史分销提成、赔偿款等来源；分销仅迁历史；不生产双写；服务端 BFF 不复制业务规则。资金/订单/审批/审计 RPO ≤ 5 分钟、核心 RTO ≤ 1 小时，以演练证明，不能由本文放行。[Tracker](../planning/rebuild-development-tracker.md)、[技术决定](../architecture/technology-decisions.md)、[BFF](../architecture/multi-client-bff.md)

## 3. 数据价值未发挥的具体证据

1. **C：旧首页与利润列表不是同一统计群体。** IndexServiceImpl.console 的利润/分销/包赔计算按 pay_time 取已付并排除当前取消的订单；首页销售额和订单量则统计已付订单，取消额/量另外列出，不能将排除规则泛化到全部首页指标。利润列表限定已完成订单，可按支付或确认时间筛选。首页全额包赔还关联当前账号 is_full_payout 并乘固定 0.08；利润列表读取订单 full_payout_money。[E7,E3] **I：**同一个“利润”标题可能因时间、状态和可变维度产生不可比结果；不能据此断言生产报表曾出现具体金额差异。
2. **C：旧首页访问量求和 IndexVisit.visit；visit 按 IP、terminal、当日查找并加一。** 没有在这条链中形成搜索→详情→报价→付款的关联事件。[E9] **I：**不能把该访问次数叫独立用户数，也不能据此计算用户转化漏斗。前端实际调用覆盖仍为 U。
3. **C：旧财务概览按 refund_status 的本地成功汇总退款。** 结合既有 Joinpay 研究的终态保存缺口，**I：**该数字不足以证明渠道现金已退。[E6,E11]
4. **C：exportProfitList 先 selectJoinList 取得匹配全量记录，再写 Excel。** **I：**大量数据时可能争抢 API 内存与数据库资源；本轮没有压测，不能宣称已证实性能故障。[E3]
5. **C：旧客服和资金操作存在混用状态/日志/外部调用的链路；部分聊天调用只记录异常文本。** **I：**仅按“订单完成”“已建群”统计员工效率容易误导，必须有实际接待和交付事件。[E4,E8]

## 4. 按岗位设计工作流，而非再堆一个大屏（R）

以下岗位是分析视角，不是硬编码角色或权限；一个人可兼岗，审批仍须独立。

| 使用者与决策 | 工作入口与必要上下文 | 完成后的证据/效果 |
|---|---|---|
| Owner：今天哪里需介入，新增供给还是改善交付？ | 总览只显示异常变化、待决策事项、分游戏供需、数据覆盖；可下钻原对象 | 每张卡有责任人/下一步；观察积压是否消除，不以数字上涨自动归因经营成功 |
| 运营：审核排队、供给闲置、用户反复被退回为何发生？ | 审核队列按时限排序，保留版本差异、拒绝原因、再提交记录；可租账号与占用时段对照 | 完成审核后通知可追溯；看到后续出租和投诉，避免只追求通过量 |
| 客服：下一单该接待/交付/验收，谁能接手？ | 我的待办、即将超时、转交队列；订单上下文、交付清单、群链接、资金只读状态 | 人工确认主体和时间，转交前后责任归属；同时看等待与纠纷，避免按消息量排绩效 |
| 财务：何时能付款，哪笔不一致？ | 按账户/币种的待执行、未知、失败、待对账队列；审批快照与收款对象 | 申请→审批→执行→渠道结果→对账完整；差异只能追加说明/更正，不能改源行消差 |
| 技术：故障是否影响交易，重试会不会重复扣款？ | provider/任务异常及受权技术监控；requestId、租约、原幂等键、最近结果 | 查单/补偿记录可追溯；不在运营工作台放任意 SQL、shell 或直接改状态按钮 |

共通交互验收：数字显示“截至何时、统计范围、缺失量”；空值、0、未知、加载失败分别表达；筛选和下钻保持同一口径；并发处理提示“已由他人更新”；批量处理逐项授权和反馈；危险动作显示后果、申请快照与证据；键盘操作、焦点、颜色之外的状态文本纳入页面验收。上述是产品建议；本轮有限浏览器只读观察见 §11，没有执行完整 UX 任务测试。

## 5. 分阶段场景与最小指标字典（R）

先从已授权业务动作中获取服务端事实，再为确有决策需要的浏览行为加最少采集。三类值分开展示：**业务事实**（应付、状态迁移、人工确认）、**渠道事实**（验真回调/查单/账单）、**分析派生值**（比率、时长、分群统计）。派生值永远不能回写账本或驱动付款成功。

通用契约：存储明确时区的时间，经营日暂建议 Asia/Shanghai，渠道账务日单独按正式账单定义；窗口为半开区间 `[start,end)`；记录发生时间与入库时间，不用入库时间冒充发生时间。所有指标带 definition_version、as_of、过滤条件、完整性、水位和来源。分母 0 显示不适用；未成熟 cohort 单列；迟到/更正重算受影响窗口并标修订。以下不是已存在表结构或已验收指标。

| 场景/指标与阶段 | 问题、粒度和事件时间 | 口径/分子分母 | 排除与可得性/回溯限制 |
|---|---|---|---|
| 审核积压/时长，M3 | 是否增派审核；每次提交版本；提交、结论时间 | as_of 未结论提交数；已完成轮次的结论−提交时长 P50/P90，未完成另列年龄 | 撤回单列，不把重复提交当新账号；新提交历史可采，旧 release log 完整性待查 |
| 供给出租利用率，M3–M4 采集供给/预占，M6 后形成实际出租指标 | 哪类供给短缺；账号×时间段；状态有效区间与确认起租/归还时间 | 有效租赁占用秒数 /（可出租空闲秒数+有效租赁占用秒数）；分别列未付预占与已付款待交付 | 区间须互斥并裁剪到观察窗；出租中暂停新供给不抹除已发生租赁。维护、审核、下架的空闲区间排除；旧当前 status 不可反推历史区间，M4 订单占用不能代替实际出租 |
| 报价到付费订单转化，M4–M5 | 报价后在哪里流失；报价 cohort，quote_id/转换的 order_id | 固定观察窗内付款确认的报价数/有效报价数，每报价至多计一次；观察窗设计卡冻结 | 排除测试、机器人已识别流量和失败报价；过期、未成熟单列；无 quote_id 不补造历史漏斗 |
| 支付尝试成功率，M5 | 哪个渠道存在问题；attempt_id、发起 cohort | 观察窗内验真成功尝试/已发起尝试，未知与处理中另列，不仅除以终态数 | 业务订单成功率另算，重试不能膨胀订单数；组合支付关闭；历史标识缺口显式展示 |
| 接待/交付等待，M6 | 是否排班不足；每订单，支付确认→首次人工接待→交付确认 | 各阶段时长 P50/P90；超时未接单数及年龄；自然时长与工作时长不可混用 | 排除测试；取消单独分组；服务时段规则未定则仅自然时长；建群/消息发送不代替接待 |
| 争议率及解决时长，M7 | 哪类账号需改善；交付 cohort、争议创建/关闭时间 | 观察窗内有争议的已交付订单/同 cohort 已交付订单；时长按争议实例 | 撤回、重开关系保留，订单去重；未成熟 cohort 单列；聊天内容不能自动补成结构化争议 |
| 应退未退余额/年龄，M5–M8 | 哪笔资金需处理；退款义务，批准/到期、渠道完成时间 | as_of 已生效应退−已确认分配退款；按义务余额汇总，不相减全部收款 | 待审批、未知、已执行待核验分别列；部分退款一对多；本地旧成功不足以补渠道完成时间 |
| 渠道收支与差异，M8 | 资金是否对得上；商户/产品/账户/币种/账务日 | 各类已确认收款、退款、代付、费用、结算分列；未匹配金额与笔数，不把结算重复当经营流入 | 样例与账户映射受 IN-03 阻塞；现金流全量分母未完整前不声称“全部”；余额支付不算外部新收款 |
| 订单贡献额，M7–M8 | 哪类订单实际贡献；已结算订单、结算时点 | 经冻结映射的平台收入分录−已确认直接成本分录；包赔费/赔付、手续费分开，不重复计已净额扣除项目 | 不叫净利润；税费、工资、云成本未覆盖；账务确认口径由财务设计卡核准；缺成本显示不完整，不当 0 |
| 复租率，M8 或上线后 | 服务是否带来回访；内部用户首单交付 cohort | 固定 N 日内发生第二个已付租赁订单人数/有完整 N 日观察期的首单用户数 | N 待经营决策选定；排除取消/测试，退款另分组；跨端用内部 user_id，旧疑似同人不自动合并 |
| 内容辅助转化，按需求后置 | 改枪码/资讯是否帮助找账号；内容版本与会话 | 有效内容访问后观察窗内报价/付费的关联比例；明确为相关性 | 首期未有归因与采集需求可只记复制次数；去重、同意/用途策略先定；不能将 IP 当人或宣称因果 |

先上线审核、供给、等待、资金异常四类可行动指标；复租和内容分析在样本成熟后开放。未决定的观察窗只是展示契约的待定项，不阻塞现有 FND-002，也不授权采集所有用户行为。

## 7. 查询隔离、安全与恢复（R）

**起步阶段：**仍使用统一业务模块和 PostgreSQL。管理聚合经服务端读接口，固定查询范围、分页、超时、并发和授权；不让浏览器/BI 直连交易库。受控统计读取只需所需字段。高风险动作重新读取事务事实，不能依赖缓存看板。独立连接池/数据库角色按最小权限设计，但同一数据库实例的 CPU/IO 仍共享，不能称为完成负载隔离。

**出现实测压力后：**记录关键交易延迟与报表耗时/扫描量，先限制大查询与导出，再为反复使用的指标增加可重建汇总；刷新错峰、有水位和版本，不能因汇总失败阻塞付款。长导出通过既有任务设施异步运行、有行数/范围上限。若交易目标仍受影响或需要大范围临时查询，再评估只读副本/独立分析库；必须处理复制延迟、删除传播、权限及恢复，不把副本当即时权威。是否拆 worker 部署按任务负载确定，统一代码不等于一个运行进程。

**有跨源分析需求后：**才评估 ETL/数仓/BI；准入输入是明确问题、数据规模、刷新时限、成本和运维责任，不能仅因为“未来做数据分析”先建架构。本文不采购选型，不承诺固定 QPS 或容量。

**权限与隐私：**运营只看所辖范围；客服按订单责任授权；财务可核验收款快照但默认脱敏；Owner 看聚合不自动获得所有秘密；技术不能靠运维身份绕过业务授权。聚合/下钻/导出三个入口采用相同数据范围；防止小群体与多次筛选还原个人。报表不收身份证、银行卡、密码、IM token、原始请求体或聊天全文；证据按需引用受权存储。

导出是独立权限，记录申请人、目的、筛选/字段/指标版本、数据截至时点、记录数、文件摘要、下载与到期状态；生成与下载时重新校验权限，撤权后链接不可继续使用。表格文字防公式注入，文件用私有存储与限时授权。批量资金操作不因导出能力获得授权。

保留/删除策略按数据分类确认，不在本报告虚构法定期限。追加式账务/审计与个人信息删除可能冲突：建议从初始模型分离必要业务标识与可去标识化个人资料，建立受审批的保全/保留例外和可审计删除流程；不得擅自修改冻结的不可变审计规则。上线前由 Owner 协同相关专业人员确认用途、期限、保全和匿名化方案，必要时形成明确例外决定，未决定前不做全量正文采集。

备份不是永久分析归档。M10/M11 演练同时验证业务事实、审批/审计、私有证据引用、密钥可用性及重建统计水位；报表标明恢复后缺口，不能拿旧缓存继续显示“实时”。删除/匿名化记录须在恢复流程中重新应用，避免备份恢复使已删除个人资料再次开放；具体保留策略待确认。既定 RPO/RTO 以关键事实的实测为准，分析汇总可重建，其单独恢复时限另列，不稀释资金目标。
