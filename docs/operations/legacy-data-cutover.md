# 旧平台数据迁移与正式切换

本说明汇总旧数据迁移的已确认范围、初始化边界、历轮测试教训和正式切换要求，供脚本开发、演练和运维共同使用。字段映射以[旧数据转换与字段映射](../architecture/legacy-data-mapping.md)为准，资金和续办分别见[资金承接矩阵](../architecture/payments-and-funds.md#7-新旧资金承接矩阵)及[旧单续办](../architecture/legacy-trade-continuation.md)。

**状态：测试服已使用第七轮数据副本；正式切换的一键流程及完整生产演练尚未验收。** 已有本地迁移执行器、阶段脚本、读回与恢复能力，但它们仍有本机资源和路径约束，不能当作可直接在生产执行的一键方案。测试服使用模拟资金，不证明真实汇聚收款、退款或提现已验收。

下一轮转换目标使用正式结构；如需测试服模拟旧单退款，须在独立测试副本完成 0191 后安装并核验测试专用模拟结构及 `demo-legacy-cancel.sql`。现有第七轮安装器绑定其原库，不能直接用于新目标；新测试目标的装配和验收尚未完成。正式环境不安装模拟结构。

## 数据范围和来源

本次方案从一致的完整旧源中选择业务数据，并非把全部旧账号和订单迁入：

- 用户主体及其有依据的联系方式、身份、银行卡和邀请关系按各自规则承接；空号、冲突、冻结或注销必须保留真实状态，不能创造手机号、实名或成年结论。
- 出租账号保留截点正在上架的账号，以及存在至少一笔纳入范围订单的账号。订单逐笔筛选：旧租赁付款记录中 `order_type=1` 且 `pay_is=1` 才纳入；已付后取消、退款或仍在履约的订单及其关联事实仍保留。没成功付款记录的订单排除，包括订单自身标已付但无成功付款记录的情况。
- 若付款记录标成功、订单自身却标未付，不得静默改写事实；当前读取能力遇到这种冲突须停止并列为待处理。旧业务标记用于筛选，不等于已独立核实汇聚渠道到账。
- 迁入时已下架的历史账号保留记录，不在原账号上重新上架；截点在架账号承接后按新平台规则暂停或恢复。迁入时在途订单保留真实占用与续办责任，完单后的账号按新平台终态处理。
- 旧平台上架保证金已由业务侧确认无未退余额，此项不迁入新平台；新平台号主保证金和租客押金仍是不同的业务概念。正式切换前应再次核实这一前提。
- 旧管理员、旧订单群和聊天记录不迁入。新平台使用自己的管理员、权限和客服能力；旧在途订单由客服继续处理，需要时按现行能力为旧单新建群。

保留原始源备份与来源标识。历史支付、退款、提现、佣金和余额记录按各自合同承接；不能把历史记录直接冒充新平台渠道成功，也不能因为目标缺字段而生成零值。用户当前余额以确认的旧源截点值建立期初，旧余额流水供追溯，不再回放叠加到期初。未结收益、退款与佣金需核对旧状态和覆盖范围，不能重复入账或退款。

迁移审计压缩或归档不得删除新平台办理过程中生成的业务依据：旧单的原始资料核实、双方确认、结算和退款处理记录须随业务数据保留。迁入时仍在履约的旧单，不能把迁入时账号数量或比例当作下单快照；原始依据不足时由客服与双方核实，再按当前规则结算。

在途旧单的续办资料需保留未删除的原佣金及已结算佣金的来源记录，包括软删除但标为已结算的记录；仅未删除且待结算的记录可形成待处理佣金责任。若原记录显示佣金已结算，特殊取消须阻断并交客服核实，不自动追扣或重复入账。来源集合和原始记录摘要须从同一快照独立核对，不能只核待结算数量。

旧单状态 2「待上号」、6「待验号」和 7「待确认额外消耗」保留原状态并单列人工处理；当前自动续办只承接 3、8、9，不能将其他状态改写为进行中。源退款缺少可识别的原订单 ID 时，现有导入按待核阻断，不仅凭订单号补造关联。

恢复源备份时应核对实际导入的文件字节与摘要，隔离源实例并在只读状态下采集；原库导出结束时间不等于已证明跨表一致。恢复、采集、转换准备和目标读回分别保留同一来源的绑定，导入报错或出现需要核对的告警时停止，不将部分恢复作为可用快照。

## 新库初始化与旧数据转换分开

| 类别 | 来源与处理 | 必须检查 |
| --- | --- | --- |
| 数据库结构 | 使用选定版本的生产 initial、其后规范迁移和运行权限 | 全部业务表及有效列的中文 `COMMENT`、约束、触发器、序列、版本账、表和列级 ACL；结构已存在时按实际迁移合同处理，不重灌覆盖 |
| 静态系统数据 | 由经评审的 `initial_data.sql` 承接适合新库的固定初始值 | 固定角色/权限及其他已明确纳入的种子逐项核对；现阶段的实际内容见[业务数据库新装基线](database-initial.md)，不能假定全部业务策略都已包含 |
| 业务政策和目录 | 按确认的初始化来源装配游戏、价格、皮肤/物资目录、地区、会员、信用、分销、退款等待期和法律文书 | 标记来自旧源、固定默认、运营配置或待审核；验证内容、启用状态、引用和读取。两份平台文书须按审定版本成对封存和生效并验证公开读取及登录接受；内置帮助文章不代表协议已初始化。默认值只用于新库，不能在后续启动时覆盖运营改动 |
| 历史业务事实 | 从同一冻结旧源提取并按领域合同转换 | 用户、账号、订单、付款、退款、余额、银行卡、邀请、佣金、在途责任和媒体引用逐域对账；缺失或冲突保持待核 |
| 环境身份和密钥 | 在目标环境受限配置中提供 | 新建管理员按正式流程初始化，两位 Boss 首次自行改密并设置 TOTP；已有环境升级不得误重置账号、TOTP 或已使用的银行卡/身份摘要密钥 |

账号价格及比例须区分原始字段、旧站计算依据和迁入后的展示：可证的原比例与数量保留原值，不用四舍五入后的金额反推冒充原比例。新来源的展示包必须明确包含采集时账号比例与包赔选择，并分别核对已知、未知数量；两项缺失时在新轮次写入前停止。旧数据补录使用单独的采集事实表，新完整来源可以在展示快照中直接承接同样事实；两者均不能冒充订单下单时的冻结数据。原在架账号当前测试承接口径使用同源 MySQL 设置及旧普通用户规则冻结报价；由于同截点 Redis 缓存未获确认，该结果不能自动作为正式切换的价格证明。正式切换前须重新核对旧站实际配置及报价。

在架接管源计划对本次冻结的完整旧账号文件独立核对在架集合和逐行摘要，文件读取前后均校验摘要；不能沿用上一轮账号名单或遗漏新增在架账号。第七轮专用的皮肤与报价审计仍绑定当时来源和数量，新快照的对应装配及空在架处理须另行完成与验证。

新源采集同事务保留旧游戏普通价差 `profit_dot` 和极速价差配置 `profitFirstDot`，准备阶段对来源及数值作唯一性和格式检查。缺失字段或配置须停止核对；仅取得 MySQL 值不证明旧站 Redis 中间缓存当时的实际生效值，历史源未采集时也不得假装已有同截点证据。

现行旧在架报价证据包含账号来源摘要清单且有 32 KiB 输入上限；账号较多时不能假定一次接管一定装得下。后续须先证明完整在架集合，再按受控批次承接并核对所有批次的并集与源集合；不可单纯放大上限、跳过未装下的账号或把批次成功当成全量可租。

资源单位必须按源合同转换一次，例如旧六级子弹的组与新平台的 60 发基础单位、保险卡的天数；账号截图按旧路径到 OSS 的映射核对。图片尚未上传和路径映射错误分开统计，不能因对象暂缺伪造图片或将其他账号图片误认成有效素材。

旧在架账号接管前须有与该账号及原观察版本一致的完整皮肤承接记录。已确认的空集合可按空集合处理；记录缺失、来源不匹配、词条停用或缺失时停止该账号接管，不能把未知直接当成无皮肤。

## 一键转换工具的目标合同

正常迁移应由**一次受控命令**完成已确认范围内的预检、初始化、提取/准备、转换、必要专项承接和独立读回，不靠人工逐阶段拼接或事后手工修库。它不自动覆盖现有业务库，不自动把域名切到新系统，也不调用真实短信、IM、实名或资金渠道。

优先复用 [`scripts/migration`](../../scripts/migration/README.md) 已有来源采集、数据准备、`run-local-round.mjs`、各领域正式 writer、检查点与 `readback-local-dataset.mjs`；补齐尚未串联的初始化、专项阶段和结果汇总，而不是再维护一套独立计价或财务规则。同一套核心逻辑应能在本地演练和服务器侧运行，不依赖个人电脑盘符、固定测试库名或人工登录态。

执行工具至少应具备：

1. **明确绑定输入和目标。** 记录源快照及截止、代码/规则和 initial 版本、输入摘要；核实目标实例、数据库、角色、版本账、锁、权限、磁盘及密钥版本。源、目标或版本不一致时在写入前停止。
2. **完整编排依赖。** 新库结构和政策就绪后，按主体→账号→订单与双方关联→历史资金及在途责任→余额期初→展示/持有/媒体等依赖执行，并纳入会员、信用、分销、银行卡及已确认的专项初始化。实际顺序由同版依赖合同决定，不因名称相同跳过阶段。
3. **明确记录阶段结果。** 每项给出已完成、按政策排除、隔离/待核、失败或未执行；保留原请求键、输入指纹、检查点、审计与必要恢复依据。提交结果不明时先按原键和原目标只读核对，不能换键盲目重试。
4. **独立核对再给结论。** 对同一冻结源和目标分别读取、比较，不只复用装载过程的计数或累计金额。报告按域给出源集合、纳入、排除、隔离及未处理的互斥统计，并核对逐用户余额、逐单关联、金额、状态、来源和责任。异常及其影响须可定位，不把未取到的证据显示为成功。
5. **输出可复现的报告。** 分别记录每阶段开始/结束、行数、批量大小、查询/锁等待、资源峰值、失败与恢复耗时；敏感内容放受限位置，报告和日志不含密钥、证件、银行卡或完整业务原文。

现有本地阶段和候选脚本可用于继续开发；一键入口、服务器环境装配、全流程异常恢复、最终对账和正式切换仍需实现并用同版实测，不以脚本文件存在当作已交付。

### 当前脚本的覆盖与整合方向

| 环节 | 当前可复用能力 | 需要补齐或重新验证 |
| --- | --- | --- |
| 冻结和选源 | `capture-local-source.mjs`、`prepare-local-dataset.mjs`、`verify-full-source-population.mjs` 支持本地源采集、准备和范围核查 | 与最终一致性备份及实际 MySQL 环境绑定；从完整源证明“当前在架 + 成功付款订单”集合及排除原因。按源订单逐笔筛选，不能因为账号另有已付单就保留其未付订单 |
| 空库与基础数据 | `migrate:business --initial`、`build-business-initial.mjs`、`bootstrap-local-reference.mjs` 分别负责结构基线、基线生成和本地基础资料 | 统一核对所选 initial、尾迁移、中文注释、运行权限及目标资源；辨别参考包含什么、排除什么。已有目标的回执不能移作新目标成功证明 |
| 核心导入 | `run-local-round.mjs` 编排核心及资金、展示、期初、持有、路径和独立读回 | 这些阶段的 ACK 只代表各自范围；同版产物、目标、依赖和原检查点须绑定。当前入口带有本地路径/资源约束，不是服务器一键切换程序 |
| 会员成长 | `initialize-local-policy.mjs` 和 `run-local-growth.mjs` 分别处理本地政策及成长来源 | 总执行器只在相应成长输入存在时编排成长；正式范围须明确成长是否必需，政策发布、覆盖、贡献和读回均不可由核心阶段成功推断 |
| 信用、分销、银行卡、在架接管 | 分别使用 `run-local-credit-initialization.mjs`、`run-local-distribution-qualification.mjs`、`run-local-legacy-bank.mjs`、`run-listed-batches.mjs` 等本地入口 | 在架入口按全源分批、先试运行、逐批提交读回及全量独立回查；这些专项仍不在当前核心轮次入口内，须核同版实现、目标绑定及专项回执，不能仅因文件存在就标为完整迁移 |
| 法律文书、地区筛选和媒体 | 本地业务基础包可成对初始化已审平台文书并保留审计；地区筛选和媒体另有旧图路径/上传工具 | 轮次入口核初始化回执及两篇当前生效版本，但尚不自动运行管理员和业务包初始化；公开读取、登录接受、地区字典、路径关联及 OSS 字节仍需分别验证。路径映射成功不等于远端文件已存在 |
| 第七轮副本补充 | `complete-r07-account-capture.mjs`、`close-r07-clone-invitation-counts.mjs` 用于受限副本的采集事实及邀请覆盖补充 | 两者具有特定副本准入，不能直接复用于任意新库；新完整来源分别通过展示快照和邀请事实阶段承接，仍须在新空库验证逐条字段及覆盖结果 |

核心读回发生在旧分销资格正式承接前，证明当时的旧关系和未绑定政策状态；随后发布分销政策、承接资格并对同一源和目标独立读回。不能用后续结果改写原核心回执，也不能仅凭核心读回认定分销已初始化。信用初始化同样需要按用户状态分类与独立读回；冻结、注销和需人工核对的主体不能一律算作已初始化。

正式入口建议保留与现有工具一致的三种操作：只读计划/预检、完整执行、原运行的检查与恢复。冻结一次源码、输入、目标和执行范围后，正常路径内部串行编排必要步骤，不让操作者为每个普通阶段手工生成回执或反复拼命令；每阶段仍需自动核对前置与结果。是否重用现有入口或增加薄编排层，以能消除硬编码和覆盖全部必需阶段的最小实现为准。

### 每轮必须逐项验收

| 范围 | 关键断言 |
| --- | --- |
| 结构和新库配置 | 表、有效列、中文注释、版本账、索引、触发器、函数及 runtime 权限与同版合同一致；短信登录限流、游戏目录、定价、会员、信用、分销、地区和必要文书均有明确来源与生效结果。未启用或待业务确认的配置不能被写成已完成 |
| 用户与关系 | 源用户集合与目标主体、原编号、注销/冻结状态匹配；手机号缺失及冲突分列。邀请人和被邀请人双向可查；邀请人数与产生佣金人数分别按已确认口径核对，覆盖未闭合不能写为完整 |
| 账号与订单 | 源/目标按稳定旧键核集合和关联；覆盖在架、在租、已结算、已付取消和未付排除。原哈夫币数量/比例、资源单位、包赔、截图路径和付款方式逐项核对；账号当前采集事实不能冒充历史订单冻结值 |
| 余额与资金 | 逐用户核旧余额和期初，历史流水不二次入账；逐单核历史付款、退款、提现和佣金及在途责任。历史记录、业务应付和渠道结果分开，核实多次付款/退款及重复经济事实 |
| 银行卡与身份 | 核旧绑卡用户映射、字段和加密密钥版本，识别冲突及注销；相同卡号被多个旧用户使用本身不能自动判冲突。旧实名资料须核姓名与证件号的源字段、完整加密存储、密钥恢复、脱敏读取和授权明文读取；旧实名与新渠道核验分开 |
| 角色与真实页面 | 使用租客、号主、客服、运营及 Boss 各自身份验证对应读取和操作；先核源→目标→API/BFF→页面。页面通过、抽样通过、迁移对账和真实渠道联验分别报告 |

除正常样本外，至少保留未付款、已付款后取消、仍在履约、付款记录与订单标记矛盾、部分退款、多笔付款、零金额、来源缺失、重复号码、皮肤/图片未匹配和历史资料仅可读的案例。对账应核具体键集及金额，不仅核总数；一个阶段未运行、部分字段未采集或覆盖未闭合时，整轮不能标为全量通过。

## 历轮需要防止的遗漏

| 问题或风险 | 下次的固定检查 |
| --- | --- |
| 空库结构或初始化遗漏，导致页面可访问但功能不可用 | 启动前核对应有表、版本账、运行角色权限和依赖；覆盖短信认证限流、分销政策及资格、会员与目录等。所有必需阶段均有正反向检查 |
| 旧账号比例、包赔、资源或支付方式有来源但页面不显示 | 同一源记录→目标字段/快照→API/BFF→对应角色页面逐段核；原比例、实际报价、付款尝试及渠道结果各自表达，历史来源不一律显示为空 |
| 全量用户已导入但邀请人数仍待核 | 核源和目标完整关系集合及覆盖证明，再更新相应覆盖状态；部分记录、已接入数量或简单把未知改为零都不等于总数完整 |
| 保留订单、退款责任、余额期初重复或遗漏 | 核付款成功筛选、订单及账号依赖、期初逐人逐分、原付款与既往退款、佣金受益人和幂等键。无法确认的责任由客服核对，不能制造渠道到账或重复发款 |
| 备份恢复后数据有但功能或权限异常 | 在独立环境实际恢复，逐项核角色、owner、序列、表/列/函数和默认权限、触发器及 RLS；不能仅比较行数，`--no-acl` 路径未证明权限等价时不能当作应用可用 |
| 快照与截图、报价配置、银行密钥来自不同截点或版本 | 标清各自来源和时点，交易数据以同一最终快照为准；截图及 OSS 覆盖单独核对，历史银行卡使用原密钥版本，Redis 等外部配置另行核实 |
| 全量导入耗时长或事务超时 | 测实际阶段和数据库计划，区分真实计算、锁等待和人工排错；按等价性验证批量和索引优化，保留事务、约束、权限和幂等，不通过关闭保护换速度 |
| 复用了上轮目标的初始化证据，或恢复后漏跑后续阶段 | 源包可复用，但结构、管理员、政策和运行绑定均须指向本轮目标；续跑逐项核原 checkpoint 与后续必需阶段，不能把部分读回提升为整轮完成 |
| 源字段先被白名单裁剪，再用同一裁剪结果对账 | 对需要承接的字段分别核物理源列、提取、目标及消费者；明确按产品决定排除的字段。裁剪后的零差异只覆盖该白名单 |
| 修改范围或删除旧功能后，脚本与构建仍使用旧模块 | 同时检查源码、迁移脚本、构建产物、依赖清单和数据库读路径；按新口径重建并验证，不靠保留过期构建绕过问题 |
| 现场临时补建表或手工恢复后，后续版本再次遗漏 | 先保存目标结构与运行结果，再以同版正式迁移和版本账承接，核对已有结构与权限；一次性修复回执不等于完整初始化脚本 |

例如，第七轮本地核心用户、账号、订单和资金观察阶段记录为 63 分 33 秒，会员成长写入为 75 分 34 秒；它们没有覆盖正式服务器的导出、传输、恢复和切流。该次成长执行覆盖 174,846 位用户，记录了 4,761,107 次数据库查询，计数包含执行前后核验和锁操作，不能单凭文件数量判断瓶颈。同次核心阶段的批次事件显示，174,846 位用户从首个批次意图到最后提交确认约 36 分 24 秒；空资金覆盖约 8 分 37 秒。这些是事件跨度，不能直接当作无故障吞吐或新版本预计耗时。另一次分销资格写入因关系检查顺序扫描发生超时，优化约束查询后同规模事务才完成。各阶段可能重叠或包含故障排查，不能简单相加，也不能据此承诺生产停机时长。

审计、历史覆盖证明和幂等回执虽可能占用大量空间，但部分直接参与权限、恢复、去重或资金责任判断。需先逐表识别读写依赖与保留期限，再评估归档、压缩或清理；不能把它们一概视为无业务用途。

### 迁移证据的体积与优化方向

第七轮迁移后的 PostgreSQL 目标库一次只读测量为 8.55 GB（约 7.97 GiB）；其中审计事件、历史财务覆盖和通用幂等回执三表合计 5.33 GB。采用的 [`pg_total_relation_size`](https://www.postgresql.org/docs/16/functions-admin.html) 包含各表索引及 TOAST，不能再把这些索引重复计入。该数值是当时的 PostgreSQL 物理占用，不等于 MySQL 逻辑导出文件、PostgreSQL 导出包大小或当前线上实时容量。

| 第七轮目标表 | 含索引和 TOAST 的物理占用 |
|---|---:|
| `zzsh_iam.audit_event` | 约 2.49 GB |
| `zzsh_order.personal_finance_observation_coverage` | 约 1.48 GB |
| `zzsh_supply.idempotency_record` | 约 1.37 GB |

同次测量的 874,230 条财务覆盖中，844,340 条的源记录数、导入数和隔离数均为零。现有空覆盖导入仍按用户和来源生成覆盖行、审计事件和幂等回执，因而无历史记录的用户也占大量空间；这并不表示可以把缺少覆盖行直接解释成“已证实为零”。旧读取、批次恢复和部分资金/订单约束仍会检查这些结构，审计和幂等表也同时供新业务使用。

下一轮候选对已证实为空的历史记录保留逐用户覆盖行，以每个固定批次的一条审计和一条幂等回执替代重复的逐用户过程记录；批次绑定原始输入、目标、经办身份和截点，独立读回仍逐项核对覆盖及批次证据。非空、隔离和未知来源不使用此路径；第七轮已有逐条回执继续使用原合同。原始输入和批次清单须在受限位置可恢复，摘要不能代替需要追溯的正文。新目标写入门禁仍关闭，该候选尚需完整转换及恢复演练。

即使转换脚本通过验证，也应为每次实际运行保留源与目标、脚本版本、阶段结果及异常的简要记录，便于对账和恢复；不要求对每个已证明为空的用户重复写入审计。旧数据的逐条业务事实、新站后续业务操作的审计和资金幂等与迁移过程日志分开处理，不因精简迁移记录而一并关闭。

如进一步稀疏化覆盖行，必须同步改造历史覆盖读取、旧单责任和原键恢复所依赖的调用方与数据库约束；仅删表、跳过写入或更改显示会使当前判断失真。正常订单、资金和管理员操作的审计及幂等继续按各自合同保留。其他重复正文或索引先逐项核依赖和等价性，再决定归档或精简。

验收应使用同一源快照，在隔离目标分别运行原实现和优化实现：比较每类用户覆盖状态、历史明细、余额与在途责任、失败恢复和重复提交；覆盖新增用户、源异常、部分成功及提交未知。分别测量写入耗时、表/索引/TOAST 大小、导出包大小、网络传输、恢复耗时和峰值资源，报告实际差异；在这些结果通过前，不预估具体可节省的 GB 数，也不修改已有测试服数据。

第七轮演示副本的 PostgreSQL 交付归档约 1.30 GB，曾在目标服务器恢复约 11 分钟；归档目录检查显示上述三表均有数据项，但尚未测量各表的压缩字节数。[PostgreSQL 16 `pg_dump`](https://www.postgresql.org/docs/16/app-pgdump.html) 的 custom 归档默认压缩；优化物理表空间不代表归档减少相同字节，压缩级别和格式须按实际工具配置、CPU及恢复耗时实测。正式切换不要求把转换后的数据库先搬回个人电脑：可评估将最终一致的旧库备份安全传至目标 PostgreSQL 附近的隔离迁移环境，再用相同转换逻辑直接产出目标库。源、目标实际网络、带宽、机器资源和该路径的完整耗时仍须演练；跨机器传输需保护访问与加密，并核对实际字节、摘要和恢复结果。

## 正式切换的建议顺序

Owner 当前可接受数小时完全停机。优先演练“停止旧业务写入→最终一致快照→全量转换→独立核对→切换”；旧站运行时预迁及增量/CDC 仅在全量方案无法满足经实测确认的窗口时另行评估，不假定现有脚本支持增量。

NEXT 轮次完整采集来源，但账号和订单按已确认的成功付款与在架选集导入；当前不支持通过 `--contact-append` 或 `--legacy-number-only` 追加写入 NEXT 目标。如需追加，须先重新证明原快照、选集、目标与追加集合的关系。

1. **维护前准备：**冻结同版代码、规则、initial、依赖及目标资源；核验云端容量、网络、源库备份方式、对象存储和保护钥，准备新环境及可恢复备份。基于代表性数据完成空库安装、全量转换、恢复与角色/页面验证，记录完整时长及失败恢复。安排客服承接旧在途订单。
2. **停写和最终快照：**由网关提供静态维护页，停止旧站下单、结算、提现、运营修改及相关定时写任务，等待在途事务并清点在途渠道请求。生成一致性快照并验证完整性；是否在目标服务器附近的隔离 MySQL/迁移机转换，由容量和演练决定，个人电脑不应是必经环节。
3. **处理异步渠道：**维护页不能代替支付回调。切换前必须设计并演练原请求的唯一接收、持久化、去重和恢复/查询方式；禁止新旧系统对同一请求重复发款。截点后才确认成功的旧未付订单按异常处理，保留原渠道依据，不静默丢弃。
4. **转换与验证：**向独立目标执行同版转换和初始化，逐域读回源目标差异，检查在架账号报价和状态、旧在途订单、余额期初、支付/退款和分销责任、银行卡及用户关系；再按实际用户、客服和管理员角色检查核心链路。关键差异未解决时不切流。
5. **切换与观察：**通过受控入口切流；旧系统保持禁止新写。检查用户登录、账号、订单、客服、退款和后台任务及渠道回调，保留旧源只读查询与受限备份。真实商户资金动作须另行完成适配与渠道验收。

回退需区分切流前后：新站尚无真实写入且渠道通知已能安全归属时，才可评估恢复旧站；新站一旦产生真实订单或资金事实，直接切回旧站会丢失新增状态，应优先停止受影响写入并修复，若确需回退须先完成经验证的反向承接和渠道核对。

## 完成标准

- 最新源与同版工具从空目标完整执行，初始化清单和每个领域都有独立对账结果，排除、隔离、未知和未处理数量可解释。
- 中断、重试和提交状态未知的恢复经过真实数据库验证，未产生重复用户、订单、余额、退款或佣金。
- 备份在隔离环境成功恢复并验证数据、有效权限和密钥；用户、客服、管理员通过实际页面完成新单与旧在途单的约定场景。
- 渠道在途和晚到回调处理、停写、维护页、切流及回退方案经过完整演练；按实测全程耗时及余量确定正式维护窗口。
- 对仍有缺口的数据和操作明确影响范围、客服处理方式和责任人。模拟支付或源业务标记不等于真实渠道到账；未测试的事项保持未验。
